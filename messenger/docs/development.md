# Разработка и поддержка документации

## Реализация

TypeScript типизирует DTO и контракты адаптеров. `SourceAdapter` — interface,
TelegramAdapter — реализация; MessengerService обращается к интерфейсу, а не к
TelegramClient. `EntityId` остаётся строкой, поэтому HTTP-граница дополнительно
проверяет адресата и маршрут во время выполнения. Типы не заменяют проверку входа.

React `useState` хранит снимок, веб-вход, `targetId` и словарь черновиков.
`useEffect` получает сессию при загрузке, затем снимок после входа, управляет
прокруткой и Escape-listener. Административный AdminApp загружается отдельным lazy chunk по /admin.
Роли и API не зависят от размера экрана. Анонимные async-callback выполняются в контексте
именованного владельца; компонент не читает SQLite или MTProto напрямую.
Fetch-функция `api` передаёт cookie и CSRF только своему origin.

Активная MessagePage хранится отдельно от Snapshot общей ленты. Номер запроса
и AbortController в useRef защищают быстрый переход между адресатами от позднего
ответа. useLayoutEffect однократно применяет план прокрутки: вниз при открытии
или с сохранением видимого сообщения при добавлении старой страницы.

Административный ConversationPicker получает типизированные props с каталогом
и общим выбранным списком. `useState` хранит только текущую папку и строку поиска;
Map по conversation ID восстанавливает порядок закреплений, Set проверяет
галочки. Смена закладки не меняет список разрешений. `useId` связывает tab и
tabpanel, `useRef` хранит DOM-кнопки для клавиатурного фокуса. Эти ссылки не
содержат Telegram-клиент или реквизиты.

Необязательный метод SourceAdapter.listConversationCatalog позволяет источнику
не поддерживать папки. Общие DTO используются frontend/backend, тогда как
Telegram-типы остаются в коннекторе. Функция telegramFolders использует
instanceof для TL-конструкторов и Set для include/exclude. Строковые marked ID
различают Telegram user/chat/channel даже при равном числовом ID.

Node.js обслуживает один HTTP-порт и собранные статические файлы. Promise
`pendingRefresh` объединяет параллельные обновления, карта `sends` объединяет
повторы отправки с тем же request ID. Это память процесса, а не очередь задач.
Вызовы провайдера асинхронны; HTTP-обработчик возвращает безопасную ошибку,
не сериализуя исходное исключение.

`node:sqlite` используется синхронно для настроек, выбора и полного кеша выбранной истории; размер SQL-страниц ограничен. Параметры
передаются через prepare/run/get, без построения SQL из текста сообщения.
Операции файлов сессии синхронны: права 0600, случайный IV, auth tag, временный
файл и rename. Key file остаётся локальным; vault не является отдельным сервисом.

CSS задаёт общую ленту и выдвижной список на узком экране. `100dvh`, safe-area,
16px для мобильного textarea и правила короткого viewport ограничивают layout.
Это проверка эмуляции, а не гарантия поведения физической клавиатуры iOS.

Палитра светлая: синий акцент `#3390ec`, белые панели, серо-голубой фон ленты
и светло-зелёные исходящие сообщения. Цвета вынесены в CSS custom properties.
Список диалогов — две строки: название/время и источник/превью. Строка адресата
компактная, поле ввода начинается с одной строки и растёт до 128 px. Пустая
строка служебных действий не занимает место. В выбранном диалоге его название
и кнопка выбора адресата не повторяются у каждого сообщения; в общей ленте
контекст и «Ответить» остаются внутри пузыря. Навигация, отправка, роли и API
сохраняют прежние контракты. Основные мобильные кнопки имеют область 44 px.
При догрузке позиция привязана к видимому сообщению, а не только к общей высоте.
Для сообщений не используется подмена высоты скрытого содержимого: браузер
менял её после восстановления прокрутки. DOM пополняется страницами при чтении.


## Исходники и справочник

```bash
bash messenger/scripts/npm.sh run docs:build
bash messenger/scripts/npm.sh run docs:check
bash messenger/scripts/npm.sh run docs:test
```

Генератор использует уже установленный `typescript` как devDependency. Он читает
AST собственных TS/TSX/MJS и статические исходники только внутри backend,
frontend, shared, scripts, test и `playwright.config.ts`. Серверы и приложение
не импортируются, сеть не нужна, `.local/` и рабочие БД не читаются.

Генерируются только `docs/reference/`: страницы модулей, перечень объявлений,
полные интерфейсы/type aliases, сигнатуры функций и методов, экспортированные
константы, HTTP-ветки, DDL и имена тестов. Прямые runtime-вызовы и выводимые
TypeScript return-типы не реконструируются. Полная JSON Schema не генерируется.
Назначение модуля хранится в реестре `purposes` генератора; новый модуль требует
его обновления. HTML, CSS, SVG и shell описываются на уровне модуля.

Перед каждым именованным классом, функцией, методом, getter/setter, типом,
интерфейсом и экспортированной константой TS/MJS стоят две помеченные строки:

```typescript
//: Строит внешний ID сущности.
//: Включает источник и экранирует компоненты.
export function entityId(sourceId: string, kind: string, nativeId: string): EntityId
```

Обычные комментарии и пустые строки не входят в описание. Именованные вложенные
функции имеют полное имя владельца; callbacks без имени описаны в его контракте.
Методы интерфейсов включены в полный интерфейс. Тесты перечислены по именам
сценариев; сторонний код не документируется.

`docs/reference/inventory.json` содержит только путь, полное имя и якорь.
Якорь `symbol-MessengerService.send` стабилен при сдвиге строк; повторное
объявление того же имени получает `--declaration-2` и далее. Нет координат строк,
даты генерации, Git SHA или хеша исходника. Изменение сигнатуры отражается только
в описании соответствующего объявления.

`docs:check` строит ожидаемые страницы в памяти, проверяет ссылки и сравнивает
побайтно. Код 1 означает отсутствие пояснений, новый модуль без назначения,
устаревшую/лишнюю страницу или битую ссылку. Локальные файлы и явные якоря
справочника проверяются; внешние сайты и произвольные heading-якоря — нет.
Команда ничего не переписывает. `docs:build` записывает только изменившиеся
страницы и не удаляет лишние автоматически.

## Порядок изменения

1. Обновить код и его две строки пояснения; сохранить текущие ограничения модуля.
2. Исправить соответствующий сценарий, API, данные или правило безопасности.
3. Выполнить docs:build, docs:check, docs:test и проверки приложения по изменению.
4. Записать результат и его границы в протокол, изменение — в журнал.
5. Проверить diff: смысловые изменения справочника должны соответствовать коду.
   Коммиты разделять по темам; уже опубликованную историю не переписывать.

Уточнение только руководств требует docs:build/check/test и git diff --check.
Новая проверка реального аккаунта или VPS из редактирования Markdown не следует.
Если код приложения и сценарии развёртывания не изменились, документационный
коммит отправляется в GitHub без перезапуска сервиса. Изменение кода приложения
проходит полные checks/deploy. Описания модулей внутри генератора справочника
относятся к документации и проверяются docs:test.

## Границы будущего расширения

Новый источник реализует SourceAdapter и регистрируется в backend/index.ts через ConnectorRegistry.
Отдельные страницы по провайдерам, автоматический выбор сервиса отправки и
передача чужих сообщений ИИ не следуют из этого расширения. Источник должен
поддерживать изолированные тесты маршрутов. Codex-клиент вне Messenger не
участвует в его runtime и не меняется ради документации этого модуля.

## Действующий контракт сервера

Core дополнен Registry, Selection и UnifiedInbox. Любая выдача снимка повторно
фильтрует ID; каждое действие проверяет выбор на сервере. Админский каталог —
только метаданные, без preview. История выбранных кешируется в отдельных таблицах;
после исключения строки не удаляются. Новая схема добавляется без разрушения
старой, что позволяет откатывать кодовый релиз без замены пользовательской БД.

В production обязательны Argon2id-пароли обеих ролей, HTTPS Origin и внешняя
директория данных. Код/2FA передаются одноразовым resolver и не становятся
полями состояния сервиса. Саму библиотеку teleproto и исходные исключения не
логировать. Runtime-этапы и настоящая Telegram-авторизация не запускаются генератором.

После отказа входа сохраняется только категория TelegramAuthIssue. Папки и
закладки используют текущий каталог метаданных; разрешения определяет только
ConversationSelectionService. История изменений реализации находится в журнале,
а этот раздел описывает действующие границы независимо от номера прошлой версии.

Сборка и автоматические проверки выполняются локально. Развёртывание после
коммита запускается скриптом deploy/messenger/deploy.sh; пользователь проверяет
работу на сервере. UI-проверки через тестовые адаптеры не являются проверкой
реального Telegram. Подробный контракт — deployment.md.
